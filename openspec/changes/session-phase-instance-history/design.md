## Context

`EngineState` (`src/domain/session/engine-state.ts`) is the pure, wall-clock-free state for a live `PhaseGraph` traversal — `tick` actions just decrement `remaining`; nothing in `engineReducer`'s switch reads `Temporal.Now`. `Session`/`PhaseInstance` (`src/domain/session/session.ts`) already exist as types (one full graph traversal, made of one record per phase visited — `plannedDuration`, `actualDuration`, `startedAt`/`endedAt`, `endReason`, `activeItem`, `itemsTouched`, `mutationsApplied`) but nothing populates them for real. `src/timer/reducer.ts`'s `synthesizeHookContext` fabricates a throwaway `PhaseInstance`/`Session` on every hook invocation instead — fresh random ids each call, an inline `Temporal.Now.instant()` read, `activeItem`/`itemsTouched`/`mutationsApplied` hardcoded to `null`/`[]`. Every field is commented "superseded once flow-c08 lands" (`engine-state.ts`'s own doc comment: "Deliberately does NOT embed a `Session`/`PhaseInstance` history yet ... only means something once Hook/CompletionPolicy execution ... exist"). Those dependencies (flow-xn3, flow-qx9) are closed, so this design replaces the placeholder.

`EngineStore.dispatch` (`src/timer/store.ts`) is this codebase's one impurity boundary: it calls `engineReducer` synchronously, applies the resulting state, derives which `onEnter`/`onComplete`/`onSkip`/`onExit` events fired (`deriveHookEvents`, pure, reads pre/post `EngineState` + the action), then resolves and `await`s each fired event's hook and applies its returned `FileMutation[]`. It already has a working precedent for "impure external state needs to reach a pure reducer": `syncQueueExhausted` reads `TaskSourceRegistry`, then feeds the result back through `engineReducer` via a dedicated, store-internal-only `EngineAction` variant (`set-queue-exhausted`) that no external caller ever dispatches. `phaseVisitCounts` is the same shape again — runtime state the reducer accumulates and reads back, not part of the static `PhaseGraph`.

Two facts surfaced during adversarial review (two independent Opus-model reviews — a Software Architect on architecture/correctness, a UX Architect on forward-looking data-shape adequacy — both verified against the real code, not just the proposed shape) materially change what this design covers:

- **Every `EngineStore.dispatch` call site in this codebase is fire-and-forget** (`void this.store.dispatch(...)` — `src/main.ts`, `src/views/side-panel-view.ts`, `src/views/timer-view.ts`, `src/views/status-bar.ts`, `src/timer/ticker.ts`). `dispatch` is `async` and awaits `invokeHook` internally, but nothing serializes overlapping calls. Today this never manifests: with no hooks configured, `dispatch` never yields (no `await` reached) and one dispatch runs to completion before the JS event loop can start another. The moment a real hook is registered (`hookRegistry`/`port` both non-`undefined`), `await invokeHook(...)` yields mid-`dispatch`, and a queued `tick` or a button click can start a second `dispatch()` that reads/writes `this.state` while the first is still in flight. This is a **pre-existing, independently-valuable correctness bug**, unrelated to what `Session`/`PhaseInstance`'s shape should be — but stateful history tracking is what turns it from "theoretically possible" into "will corrupt session history in practice." See External Prerequisite below.
- **`TimerTicker` stops on pause** (`src/main.ts`: starts the ticker only while `state.status === 'running'`). So a tick-derived duration (based on `remaining` deltas) measures *focused* time excluding pauses, while a wall-clock `endedAt − startedAt` span includes any pause. These diverge on any paused phase — the design must say which each field represents.
- **`start` is dispatched for two different purposes**: beginning a genuinely fresh session (from a `stop`-reset state) and, carrying a `filePath`, re-targeting the active task mid-session (`side-panel-view.ts`/`timer-view.ts` dispatch `{type:'start', filePath: item.sourcePath}` from a task-list click). Session-open logic must be idempotent under the second case.

## Goals / Non-Goals

**Goals:**
- Give `EngineState` a real, engine-maintained `Session`/`PhaseInstance` history: explicit session-open/close semantics, a real per-instance open/close lifecycle (stable ids, real timestamps, snapshotted phase/item data that survives later config edits), and a principled way for `Temporal.Now` to enter an otherwise wall-clock-free `engineReducer`.
- Delete `synthesizeHookContext`; `HookContext.instance`/`.session` become reads of real state, not fabrications.
- Preserve `engineReducer`'s purity and the existing "store resolves external/impure state, reducer stays plain" split (`queueExhausted`/`phaseVisitCounts` precedent).

**Non-Goals:**
- Populating `PhaseInstance.mutationsApplied` with real hook-outcome data (see Decision 7 and External Prerequisite/Follow-ups).
- Capping or windowing `Session.history`'s length (see Decision 8).
- Widening `PhaseInstanceEndReason` beyond `completed`/`skipped`/`abandoned` (see Decision 10).
- Recording a `FileMutation`'s prior value (see Decision 11).
- Fixing `EngineStore.dispatch`'s lack of serialization. Genuinely necessary before this design's own tasks can be implemented safely (see External Prerequisite), but it's a store-level concurrency fix orthogonal to `Session`/`PhaseInstance`'s shape — tracked as its own bd issue, not this change's tasks.md.

## Decisions

**1. `now` is stamped onto the dispatched action by `EngineStore.dispatch`, not threaded as a bare reducer parameter or folded into `EngineDeps`.** `EngineStore.dispatch` reads `Temporal.Now.instant()` once and stamps it onto the action for any type that can open/close a `PhaseInstance` (`start`, `tick`, `finish-phase`, `advance-phase`, `stop`) — mirroring the `set-queue-exhausted` precedent exactly (store resolves impure state, feeds it back via the action). *Alternative rejected: a new bare positional `now` parameter on `engineReducer`.* Forces every existing call site — including `syncQueueExhausted`'s own `set-queue-exhausted` dispatch (which has no use for a clock) and every direct reducer unit test — to thread a value most of them don't need, which is exactly the "fake a collaborator doesn't care about" anti-pattern `EngineDeps`'s own doc comment calls out avoiding. *Alternative rejected: add `now` to `EngineDeps`.* `EngineDeps` is documented as "optional collaborators"; a clock isn't optional/collaborator-shaped the way a registry is, and every real call needs one.

**2. `EngineState.session: Session | null`, not inferred from state shape.** Inferring "fresh session" from e.g. `currentPhaseId === graph.phases[0].id && phaseVisitCounts === {}` is unsound: a cyclic graph (work→break→work→long-break-every-4th) legitimately revisits `phases[0]` mid-session, indistinguishable from a true fresh start under that inference. `stop` clears `session` to `null` (matches `initialEngineState`'s existing full reset, and `EngineStore.setGraph`'s reset path, which calls `initialEngineState` too). `start` opens a new `Session` only when `session` is currently `null`; when non-`null`, `start` leaves session identity untouched (it may still update `activeFilePath`, its existing re-targeting behavior) — `start` and `resume` are already distinct actions, so there's no ambiguity between "begin" and "continue."

**3. `Session.currentInstance: PhaseInstance | null`, separate from `history: readonly PhaseInstance[]` (closed-only).** An in-progress instance (`endedAt: null`) sitting inside something named `history` reads oddly and forces every consumer wanting "completed instances" to filter the trailing open one back out. Matches this codebase's existing style of separate explicit fields (`queueExhausted` as its own field rather than folded into `phaseVisitCounts`). Any "live" stat (e.g. "focus time so far today") must union `currentInstance` with `history` — an implementation concern, not a shape gap.

**4. `engineReducer` owns instance open/close, including `endReason`; `deriveHookEvents` reads it instead of re-deriving it.** Today `endReason` is computed independently in `deriveHookEvents` (`'completed'` for a natural conclusion, `'skipped'` for `advance-phase` off a running/paused state, `'abandoned'` for `stop` mid-phase) while `advancePhase`/`completePhase` separately drive the same status transitions — two derivations that must agree forever. Once the reducer mints instance lifecycles as part of the same pure transition that already changes `currentPhaseId`/`status`, it can write `endedAt`/`endReason`/`actualDuration` onto the closing instance directly, and `deriveHookEvents` reads `endReason` off `nextState`'s just-closed instance rather than recomputing it — one source of truth. `HookEventOccurrence` gains `phaseInstanceId: PhaseInstanceId`, minted by the reducer at open time, so a fired event can be attributed to the exact instance it belongs to — required because a cyclic graph revisits the same `phaseId` repeatedly, so `phaseId` alone can't disambiguate which visit a firing belongs to (this is also what lets `synthesizeHookContext` be deleted outright — see Decision 9).

**5. Item tracking snapshots at activation, not at close; per-touch records, not bare ids.** The task queue is live and mutable (Bases-query-backed) — resolving `activeItem` "once, at instance-close" (as originally considered) is wrong: by close-time an item's `cycleStatus`/`timeSpent` have changed, or it may have been filtered out of the queue entirely. Instead, `EngineStore` snapshots a lightweight record — `id`, `sourcePath`, `displayName` only, deliberately excluding the mutable `cycleStatus`/`timeSpent`/`lastCycledAt` that would go stale — at the moment an item becomes active (when a `set-active-file`/task-click resolves to a queue item, via `taskSourceRegistry`, the same "store resolves external state before dispatch" pattern as `queueExhausted`). `itemsTouched` becomes an array of these records rather than bare `TaskQueueItemId`s: a bare id from a live query is not guaranteed re-resolvable later (the note can be renamed, moved, or drop out of the query), so an id-only record can go permanently dangling — a genuine dead end, not something a later change could cheaply patch, since patching it means changing *when* data is captured, not just adding a field. `PhaseInstance.activeItem` as a separately-tracked field is removed; "the current active item" is derived as the tail of `itemsTouched` when non-empty.

**6. `PhaseInstance` snapshots `phaseDisplayName`/`phaseKind` at close, alongside the already-existing `plannedDuration` snapshot.** `PhaseInstance` today carries only `phaseId`, but `Phase`s (and the graphs containing them) are user-editable and deletable. Even a simple aggregate stat ("total focus time today") needs to resolve `phaseId` against the *current* graph to know which instances count as focus — which breaks silently on a rename/re-kind and breaks loudly on a delete. `plannedDuration` is already snapshotted onto the instance for exactly this "survive config drift" reason; extending the same treatment to the phase's display name and kind is the same pattern applied consistently, not a new one.

**7. `mutationsApplied` is explicitly cut from this change's scope.** A hook's own `FileMutation[]` return value is only known strictly after the reducer transition that closed its instance already happened — folding it back requires an async, store-driven second write into already-closed history, which needs: reentrancy handling (a later dispatch can run mid-`await`, and by the time a hook settles, its target instance may already be several instances back in `history`, or `session` may have gone `null` via an intervening `stop`); append-not-replace semantics (`onComplete` and `onExit` both fire for the same closing instance and settle independently); a "sealing" answer (does a closed `history` entry keep mutating after close, visibly to subscribers?); and a home for hook-invocation *failures* (`PhaseInstance` has no field for a failed/`invocationFailed` outcome today). That's real design surface in its own right, and it isn't needed for this change's actual goal — a hook's own not-yet-known return value was never something its *own* `HookContext` needed to show. `engine-state.ts`'s existing doc comment already frames `mutationsApplied` as "follow-up work, not this pass"; this decision honors that rather than overturning it. Tracked as a separate, dependent follow-up bd issue.

**8. Unbounded `history` growth is an accepted non-goal for this pass.** `EngineState` is not persisted anywhere today — confirmed by inspection: only plugin `settings` round-trip through `loadData`/`saveData` in `main.ts`; `Session`/`PhaseInstance` have no Zod schema or serialization path. Growth is therefore in-memory-only, bounded by one session's length and Obsidian's own reload cycle. See Risks for the forward-looking note this implies for a future persistence design.

**9. `synthesizeHookContext` is deleted.** Once Decisions 1-6 land, a `HookContext` is built by reading the real `currentInstance` (for `onEnter`) or the matching closed `history` entry (for `onComplete`/`onSkip`/`onExit`), selected by the `phaseInstanceId` on the fired `HookEventOccurrence` (Decision 4) — no fallback path is needed.

**10. `PhaseInstanceEndReason`'s 3-way enum (`completed`/`skipped`/`abandoned`) is kept as-is.** A finer split (e.g. "skipped because done early" vs. "skipped because abandoned by intent") was considered and rejected for this pass: no current UI captures that distinction at the moment of a skip, so nothing is being thrown away by not widening the enum now — it can widen later, for free, whenever an affordance to capture that intent exists.

**11. `FileMutation`'s `frontmatter` variant recording only the new value, not the prior one, is a known and deliberately out-of-scope gap.** A future "what changed" summary would show to-value only, not from→to. Not built speculatively.

## External Prerequisite

**`EngineStore.dispatch` needs to serialize overlapping async dispatches before this change's implementation session begins.** As described in Context, every call site fires `void store.dispatch(...)`, and `dispatch` already `await`s hook invocation internally without any queue/mutex around `this.state` reads/writes. That's a latent bug today (currently unreachable because no hook yields control mid-dispatch) that stateful, per-instance history tracking makes load-bearing: once instance open/close lives in `EngineState`, a race here doesn't just risk a stale read, it can corrupt session history (e.g. two instances closing out of order, or a `stop` racing an in-flight tick's instance-close). This is being filed as its own bd issue — a store-level concurrency fix, independent of `Session`/`PhaseInstance`'s shape — and this change's tasks.md assumes it's resolved first, rather than re-solving it here.

## Risks / Trade-offs

- [Unbounded `Session.history` growth for a long-running session] → Accepted for this pass (Decision 8); in-memory-only today. **Forward-looking note for a future persistence design** (not a decision made here): `Session`'s "one array, session state derived from `history`" shape is likely a poor fit for disk persistence as-is — rewriting/rehydrating a growing array on every phase close is expensive, and a persisted design will likely prefer append-only history plus cached aggregates instead. Flagged so that future design doesn't have to rediscover this from scratch.
- [Cutting `mutationsApplied` from this pass leaves `PhaseInstance.mutationsApplied` present on the type but permanently empty until its own follow-up lands] → Accepted (Decision 7); the field stays in the type (no removal/re-add churn) but is documented as unpopulated pending the follow-up issue.
- [`itemsTouched`'s lightweight per-touch snapshot (id/sourcePath/displayName only) still can't answer "how long was this specific item active," since `TaskQueueItem.timeSpent` is cumulative across the item's whole life, not per-phase] → Accepted as out of scope for this pass; a future per-item-duration stat would need an enter/exit `timeSpent` delta captured at activation and at the next touch/close, which is additional capture-time work this change doesn't do. Not a dead end the way ids-only was, since the enter/exit boundary (`startedAt`/`endedAt` of the record) is still capturable later without losing anything this change already threw away.
- [Removing `PhaseInstance.activeItem` as a stored field (Decision 5) in favor of deriving it from `itemsTouched`'s tail is a schema simplification beyond what the proposal originally sketched] → Flagged explicitly rather than done silently; if a future consumer wants `activeItem` as its own field again (e.g. for a serialization boundary that shouldn't require deriving it), re-adding it is cheap and non-breaking.
- [The External Prerequisite (dispatch serialization) landing late or being deprioritized relative to this change] → This change's tasks.md should not begin the reducer/store implementation work until that issue is closed, since implementing instance open/close on top of a racy dispatch loop would bake the race into session history rather than just risk transient state.

## Migration Plan

No persisted user data exists for `EngineState`/`Session`/`PhaseInstance` today (confirmed: no serialization path, `EngineState` resets on every plugin reload) — this is a pure code migration, not a data migration. `synthesizeHookContext`'s call site in `EngineStore.dispatch` is replaced by a real-state read in the same commit that adds instance open/close to `engineReducer`, so there's no intermediate state where both mechanisms coexist. Existing reducer/store unit tests that construct `EngineState`/`EngineAction`/`HookContext`/`Session`/`PhaseInstance` literals need updating for the new/changed fields — expected and mechanical, not a design concern.

## Open Questions

- Should `PhaseInstance.activeItem`'s removal (Decision 5) be revisited if a future change needs a stable field for that concept independent of `itemsTouched`'s shape (e.g. a persistence schema)? Not blocking this change; flagged for whichever future change touches this next.
- Exact per-touch capture point for `itemsTouched` when the *same* item is re-activated more than once within a single `PhaseInstance` (e.g. a user cycles away and back) — does a repeat activation append a second record, or update the existing one? Left for `tasks.md`/implementation to pin down against whatever's simplest given `engineReducer`'s existing `phaseVisitCounts`-style accumulation pattern; either answer is compatible with this design's decisions.
