## Context

`Hook` (`src/domain/hook/hook.ts`) is already `(context: HookContext) => Promise<readonly FileMutation[]>`, and `EngineStore.dispatch` (`src/timer/store.ts:70-97`) already `await`s it — widened by the (archived) `hook-write-back-migration` change specifically so a future interactive/async hook wouldn't need `EngineStore` touched again. Exactly one `Hook` is registered anywhere today: `createWriteBackHook` (`src/timer/write-back.ts`), wired in `main.ts:42-51` as a single-entry static `HookRegistry`. `Predicate` (`src/domain/hook/predicate.ts`) is a separate, deliberately narrower type — `(fromPhaseId, visitCounts) => boolean`, synchronous, no I/O, called inline inside the pure `engineReducer` because it decides `EngineState.currentPhaseId` itself. Zero predicates are registered anywhere (`main.ts:53`: `{ resolve: () => undefined }`).

Both registries are built once in `main.ts:onload()` as plain resolve-only objects — independent of any Bases view's lifecycle, since hooks fire from `TimerTicker`-driven dispatches (`main.ts:55-59`), not from view rendering. This is unlike `MutableTaskSourceRegistry` (`src/timer/task-source-registry.ts`), the one registry in the codebase that *is* runtime-mutable, because its contents legitimately change per Bases `onDataUpdated` — its own doc comment explicitly contrasts itself against "`HookRegistry`/`PredicateRegistry` (populated once at plugin load)."

This design was reached over several rounds of adversarial review and grounded ecosystem research (see `flow-gu1.10`'s `bd show` design field for the full provenance). Two corrections from that process are load-bearing here and are not re-litigated below: (1) the reference class for the trust/isolation model is Obsidian's own built-in **Bases** formula/function system, not community script-runner plugins (Templater/Dataview/QuickAdd) — those operate under Obsidian's all-or-nothing "Restricted Mode" boundary, a different trust model than a first-party, on-by-default feature; (2) Bases' formula grammar is confirmed (via Obsidian's own docs) to be genuinely restricted — no assignment, no user-defined functions, no I/O, statically-rejected circular references — and is *not* embeddable or extensible by third-party plugins (no such API is shipped; it's an open, unfulfilled forum request).

## Goals / Non-Goals

**Goals:**
- Let a `Phase`'s `onEnter`/`onComplete`/`onSkip`/`onExit` resolve to a vault-authored `.js` script, gated by an explicit bind-time trust decision, producing `FileMutation[]` through the existing `Hook` contract unchanged.
- Let a `TransitionCondition`'s `'custom'` predicate resolve to a vault-authored formula string, evaluated synchronously in-process, with no execution isolation needed because the grammar itself has no capability to misuse.
- Give both a discovery/binding mechanism that matches how Obsidian users already expect to configure "run X when Y happens" (grounded in Templater/QuickAdd/Shell-commands convention), without reopening this project's "never eval from settings/frontmatter" boundary.
- Make `EngineStore.dispatch`'s hook loop resilient to a script that throws or hangs — necessary once hooks stop being exclusively one hand-typed, vetted implementation.

**Non-Goals:**
- Widening `Predicate`'s inputs beyond `fromPhaseId`/`visitCounts`. Vault-state-dependent predicates (e.g. an `isRestDay` example reading a daily note's frontmatter) stay out of reach until a follow-up change adds a pre-resolved snapshot input — deliberately deferred rather than pinned down speculatively here (see Open Questions).
- Any read/write bridge that lets a script query vault state *during* its own execution (an RPC-over-`postMessage` request/response protocol was designed, then dropped — see Decisions).
- Exposing interactive prompt/modal capability to vault-authored scripts. Stays exclusive to the built-in write-back hook.
- A permission system, capability tokens, or per-mutation-type ACLs layered on top of `FileMutation[]`.
- Changing `PredicateRegistry`/`HookRegistry`'s resolution semantics (`transition-predicate-resolution`'s and `hook-execution`'s existing "unresolved name → treated as absent, never throws" requirements are untouched) — only *what* gets registered under a name is new.

## Decisions

**Two separate mechanisms, not one script runner.** `Hook` is write-capable and, ideally, would defend against a script trying to reach the vault/host outside the `FileMutation[]` choke point — that's what runtime isolation would buy, if a viable one existed in this Electron build (see Decisions' erratum: it doesn't, so the actual defense is the bind-time gate instead). `Predicate` is read-only-by-contract and evaluated inline inside a pure reducer — a restricted expression grammar removes the *vocabulary* to do anything unsafe, a guarantee that holds regardless of the Hook-side isolation question. Obsidian's own Bases formulas validate this split directly: the most ambient, zero-opt-in, on-by-default feature in the platform chose grammar restriction for reads and *has no write primitive at all* — evidence that restriction doesn't scale to "safely describe a mutation," which is exactly why the Hook side needs a different (if imperfect) safeguard.

**Script hooks execute in-process on the main thread; no runtime isolation mechanism — the bind-time confirmation gate is the only trust boundary.** (This is the current decision, replacing the Worker-based one immediately below — kept in place, marked superseded, rather than deleted, so the erratum that forced this change stays legible.) A `new Function(scriptSource)`-style invocation, run directly against a real `HookContext`, is the ecosystem-standard *mechanism* — Templater, Dataview, and QuickAdd all execute user scripts in-process with no runtime sandbox — but the ecosystem-precedent argument needs one more link than "no isolation, same as them": this design's own round-2 review (see Context) deliberately moved *away* from citing Templater/Dataview/QuickAdd wholesale, because a Hook fires *ambiently* on every phase transition, unlike a template a user explicitly inserts. That distinction still holds and is not waved away here — but it doesn't apply uniformly across that ecosystem. Templater's *folder templates* (auto-run on note creation in a configured folder) and QuickAdd's *"Run on startup"* macro are already-ambient, bind-once-fire-repeatedly triggers within that same ecosystem, and both are exactly the precedents the "trust gate is at bind time, not per-firing" Decision below already cites for *that* Decision. So the honest claim is narrower than "Hooks are like Templater in general": it's "Hooks are like the ambient-triggering *subset* of that ecosystem (folder-templates, startup macros), which already accept bind-time-only consent for a repeatedly-firing action" — not like a manually-inserted template, which this design's earlier review correctly said Hooks are not analogous to. *Explicitly accepted, not overlooked:* a confirmed script has full Node/host access on every firing, with no per-firing checkpoint, same ceiling as those ambient ecosystem precedents. Stronger isolation (WASM/QuickJS, a sandboxed iframe) is real future work, tracked as flow-gu1.67, not a blocker here — see Risks and Open Questions.

> **ERRATUM (2026-07-25, tasks.md task 3.0 feasibility spike): the original Worker-isolation Decision this section replaced is false in practice.** A throwaway e2e test (Playwright/CDP against the real dev-vault Obsidian instance, not a simulated environment) spawned a Worker via `Blob`/`URL.createObjectURL` — the exact mechanism the original design assumed — and probed it from inside the Worker's own `onmessage` handler. Result: `typeof require !== 'undefined'` is `true`, `require('fs').readFileSync('/etc/hostname', 'utf8')` succeeded and returned real host data, `require('child_process').execSync` is defined, and `typeof process !== 'undefined'` is `true`. `window`/`document` are correctly absent, but that was never the property the original Decision relied on. Obsidian's `BrowserWindow` evidently runs with Node integration enabled for spawned Workers too (`nodeIntegrationInWorker`-equivalent), and that is a webPreferences setting on Obsidian's own window — not something a plugin's `new Worker(...)` call site can override per-invocation. **Practical consequence: the "no isolation at all" alternative the original Decision rejected and the Worker approach it chose instead provide the identical (zero) protection against `require('fs')`/`child_process`.** Given that, spending the Worker's real implementation cost (a second esbuild entry point, a message-passing protocol, a Temporal serialize/rehydrate boundary) for zero additional safety isn't justified — hence dropping it rather than keeping it for its non-isolation properties. (A Worker's other property, forced termination of a hung script, is given up too — see Risks.)

**`HookContext` gets pre-resolved, read-only frontmatter for exactly one context-implied path — the active file's note (`EngineState.activeFilePath`) — resolved synchronously before the script runs.** (Corrected during final review: an earlier draft of this decision also named "the firing phase's own note" as a second enrichable path. `Phase` (`src/domain/phase/phase.ts`) has no note/file-path field — `id`, `label`, `kind`, `duration`, `taskSourceId`, `completionPolicy`, `notification`, `logTarget`, and the four hook references are its entire shape — so there is no second path to resolve. If a phase-to-note association is wanted later, it needs its own domain modeling as a separate change; it is not something this change can silently assume exists.) *Constrained to the one context-implied path, not arbitrary script-chosen paths:* even without a runtime sandbox, there's no reason to hand a script a general vault-read API it wasn't asked for — the risk is vault-internal exfiltration, e.g. a script reading note A's frontmatter and writing it into note B via the existing `append` mutation, a capability never obviously granted by registering a hook for one specific phase. Constraining what's *handed to* the script keeps this true regardless of the isolation question above.

**No structured-clone/Temporal-serialization boundary is needed.** This was solely a consequence of crossing into a Worker via `postMessage`; executing in-process means the script receives the real `HookContext` object directly, `Temporal.Instant`/`Duration` values included, matching this project's Temporal-over-`Date` convention with no wire format at all.

**Execution model: invoke directly, with a `Promise.race`-based soft timeout — no Worker, no pool.** A timeout still catches the common case (a script whose returned `Promise` never settles, e.g. an `await` on something that hangs), treated as a failed invocation like any other rejection (per the group-1 per-invocation `try`/`catch`). It does **not** catch a script with a synchronous infinite loop (`while (true) {}`) before its first `await` — with no Worker, nothing external can preempt a synchronous main-thread hang. Accepted: this matches the ecosystem baseline (a bad Templater/Dataview script can freeze Obsidian's main thread too; there is no existing precedent for forced termination of a same-thread synchronous hang), and is a strictly narrower gap than "any script can read arbitrary Node/host state," which was already accepted above. *`Promise.race` marks the invocation failed; it does not stop the script.* Losing the race means `EngineStore.dispatch` moves on and treats the invocation as a failure, but the script's own `Promise` keeps running in the background — it can still resolve later, still call `require('fs')`/mutate the vault directly (per the isolation decision above), just without its return value being applied through `FileMutation[]`. "Treated as a failure" describes what `dispatch` does with the outcome, not a guarantee that the script itself has stopped.

**`Promise.race`'s losing branch gets a no-op `.catch()`, not left dangling.** Purely to suppress an unhandled-rejection warning if the script's promise eventually rejects after its timeout has already been recorded as a failure — not a mechanism that stops or contains the script (see above).

**`EngineStore.dispatch`'s hook-invocation loop (`src/timer/store.ts:82-95`) gets a `try`/`catch` around each hook's invocation, not just around `applyMutations`'s result.** Today, a hook whose returned promise rejects propagates out of `dispatch` uncaught, aborting every later fired event's hook in that same dispatch — acceptable when the only hook is one vetted, hand-typed implementation, not acceptable once user-authored scripts (which will throw and hang far more often) are in the mix. This is a genuine behavior gap in the existing `hook-execution` capability, not new-feature scope creep — see the delta spec.

**`'custom'` predicates are authored as a small formula string (comparisons, `if(cond, then, else)`, boolean operators) modeled on — but not calling into — Bases' own formula vocabulary, interpreted by a small in-repo parser/evaluator.** Bases' evaluator isn't embeddable (confirmed: no plugin extension API ships for it), so "reuse Bases" honestly means "adopt its grammar as prior art, own a small interpreter." The grammar is intentionally *not* Turing-complete: no variable assignment, no user-defined functions, no loops/recursion, no I/O — the same properties that make Bases' own formulas safe to run ambiently for every user apply here without needing a Worker, a timeout, or any serialization boundary at all. Identifier/member-access resolution in the grammar is restricted to a fixed whitelist of own `visitCounts` keys and `fromPhaseId` — not general property access — specifically to close off prototype-chain traversal (`visitCounts.constructor`, `.__proto__`) as an injection vector in a hand-rolled evaluator over user-authored strings.
**Confirmed by the user over a structured (dropdown-built) config alternative.** This track (the formula grammar and its interpreter) went through no adversarial review round — both rounds reviewed the Worker/Hook track specifically — so a structured, non-string alternative (e.g. `{ field: 'visitCounts.focus', op: '>=', value: 4 }` built from settings-tab dropdowns, no parser/tokenizer/AST, no injection surface to fence off) was raised explicitly as a simpler/safer option before committing. The user chose the formula-string approach deliberately: it's the direct analog of Bases' own formula-authoring UX (a short expression, spreadsheet-style), which is this design's explicit reference model throughout (see Context), and leaves room for more expressive/reusable authoring later if wanted, which a fixed dropdown shape would foreclose. The prototype-chain-traversal guard (below) is the concrete mitigation for the injection-surface cost of that choice.

**Predicates are configured as a name + inline formula-string pair directly in the settings tab — no scripts-folder file needed.** Unlike a Hook script (a real program, naturally a file), a predicate is a short expression; forcing it into its own vault file would be needless ceremony the grammar's restriction doesn't require.

**Discovery/binding is explicit settings-tab registration (`addSettingTab`, already wired in `main.ts:93`) for both tracks — not a vault-wide frontmatter scan, and not piggybacking on `registerBasesView`/`getViewOptions()`.** *Alternative rejected: ambient vault-wide scan for a frontmatter marker naming a script.* `HookRegistry`/`PredicateRegistry` must resolve correctly independent of whether any Bases view is open — a scan adds real costs (perf on large vaults, `metadataCache` event fan-out, last-writer-wins name collisions between two files claiming the same hook name, a startup-ordering race against `workspace.onLayoutReady`) and, more importantly, quietly relocates the trust decision into vault data one layer down: a low-friction frontmatter edit binding a name to an executable body is exactly the friction this project's "never eval from settings/frontmatter" rule (`HookRegistry`/`PredicateRegistry` doc comments) exists to preserve. *Alternative rejected: `RoutineTimerView.getViewOptions()`.* Inherently scoped to one open Bases view instance's own config — this file already has to solve "only the currently active view may safely mutate a shared plugin-level registry" once, for `MutableTaskSourceRegistry` (`registerTaskSources`/`isViewRoutineActive`); repeating that problem for hooks that must resolve whether or not any view is open at all would be solving the same architecture mismatch twice. *Chosen shape informed by ecosystem convention* (not community-plugin trust posture, just UI shape): a settings field pointing at one designated vault folder (files inside selectable by name, mirroring Templater's "user scripts folder" / QuickAdd's script picker) plus a list of named bindings, each pairing a chosen name with one selected script, added/edited via the settings tab. *Revised 2026-07-29 (dropped from the original leaning): a binding does NOT also record which of `onEnter`/`onComplete`/`onSkip`/`onExit` it's "for."* `HookRegistry.resolve(name)` takes a name only — no event parameter exists for a binding-level event selection to feed into. Which event on which phase actually fires a given name is already fully owned by that routine's own `Phase.onEnter`/`onComplete`/`onSkip`/`onExit` `HookReference` (`{ name, params }`), exactly the mechanism the built-in write-back hook already uses (`phase-graph.ts`'s `onComplete: { name: WRITE_BACK_HOOK_NAME, params: {} }`) — a second, settings-side "which events" control would affect nothing and would mislead a user into thinking it does. (The original 2026-07-25 provisional decision cited Taitava/obsidian-shellcommands' per-command "Events" tab — checkboxes attached to one command entry — as the closest ecosystem analog for this per-binding event selection; that citation is retracted along with the feature it justified, not carried forward as unused prior art.)

**Script source: plain `.js` files in the designated folder, not markdown+frontmatter or a fenced code block.** The earlier case for markdown was built entirely on "discovery via frontmatter scan" — since discovery is explicit settings-tab registration instead, that constraint no longer applies. Plain `.js` avoids YAML-escaping a script body and gets real syntax highlighting/editing, matching Templater/QuickAdd's own convention.

**Trust gate is at bind time, not per-firing.** Every ambient/automatic trigger mechanism found in the Obsidian ecosystem (Templater folder-templates, QuickAdd's "Run on startup" macro, Shell-commands' Events) treats registration/binding itself as the consent event — none re-confirms on every firing, and a per-run "this script wants to write X — allow?" modal on a hook that could fire dozens of times a day would be alert fatigue, not a recognized safety pattern (nothing comparable exists even for Dataview post-CVE-2021-42057). But a script-authored hook is less vetted than the one hand-typed hook this plugin ships, which *does* prompt interactively every run — so it shouldn't get *less* scrutiny than that hook got. Resolution: a one-time preview/confirmation shown when a binding is first created (review the script source, confirm trust for this binding), mirroring Dataview's off-by-default `enableDataviewJs` toggle-once-then-trust-forever model. No further confirmation on subsequent firings of an already-confirmed binding.

## Risks / Trade-offs

- [A confirmed script hook has full Node/host access — `require('fs')`, `child_process`, arbitrary disk/network reach — with no runtime sandbox of any kind] → Accepted 2026-07-28: matches the actual trust model of every Obsidian script-runner precedent (Templater/Dataview/QuickAdd), and the one runtime mechanism this design tried (a Worker) turned out to provide identical (zero) protection anyway. Mitigated, not eliminated, by the bind-time preview/confirm gate. Revisit via flow-gu1.67 if real-world usage shows this ceiling is too low.
- [A script with a synchronous infinite loop before its first `await` freezes Obsidian's main thread with no way to forcibly terminate it, unlike the dropped Worker's terminate-on-timeout] → Accepted 2026-07-28 as part of the same trade-off: no ecosystem precedent (Templater/Dataview) forcibly terminates a same-thread hang either. The `Promise.race` soft timeout (see Decisions) still catches an un-settled-promise hang, the more common failure mode for a hook that's supposed to return `FileMutation[]`.
- [Constraining Hook script reads to context-implied paths only means a script can't read arbitrary vault state, even read-only, for a plausible future use case] → Accepted for this change; widening is cheap and reversible later (add another pre-resolved field to `HookContext`), narrowing after shipping a wider surface is not — matches this project's general preference for the smaller, reversible cut.
- [Predicate's restricted grammar can't express anything needing vault I/O or wall-clock/date-relative logic beyond what `visitCounts`/`fromPhaseId` already carry] → Accepted and explicit: this is why `isRestDay`-style examples remain out of scope (see Open Questions), not a gap this change tries to paper over.
- [Bind-time-only confirmation means a binding, once trusted, could later be repointed at a different script file without re-confirmation if the settings UI doesn't re-hash/re-check the bound file's identity] → Needs a concrete answer in tasks/implementation (e.g. hash the script content at bind time, re-prompt if it changes) — flagged as an Open Question below rather than decided here, since it wasn't reached in the design-review rounds this document is based on.
- [Two new mutable, settings-backed registries (script-hook bindings, predicate bindings) diverge from `HookRegistry`/`PredicateRegistry`'s existing "populated once at plugin load" shape] → Accepted as a necessary, not incidental, divergence: unlike `MutableTaskSourceRegistry` (view-owned, invalidated by Bases query changes), these are plugin-owned and rebuild from the settings list on settings change — a simpler, more testable lifecycle than event-driven cache invalidation, not a reuse of the task-source pattern.

## Migration Plan

No persisted user data exists yet for either registry (`hookRegistry`/`predicateRegistry` are both empty/static today), so there's no migration of existing bindings — only additive settings schema. Rollout is naturally incremental per tasks.md: the `hook-execution` per-invocation `try`/`catch` fix lands first (independently valuable, de-risks everything after it), then the predicate-expression-grammar track (fully self-contained), then the script-hook-execution track (in-process invocation, context enrichment, soft timeout), then the settings-tab UI wiring both together.
