## Context

`Hook` (`src/domain/hook/hook.ts`) is already `(context: HookContext) => Promise<readonly FileMutation[]>`, and `EngineStore.dispatch` (`src/timer/store.ts:70-97`) already `await`s it — widened by the (archived) `hook-write-back-migration` change specifically so a future interactive/async hook wouldn't need `EngineStore` touched again. Exactly one `Hook` is registered anywhere today: `createWriteBackHook` (`src/timer/write-back.ts`), wired in `main.ts:42-51` as a single-entry static `HookRegistry`. `Predicate` (`src/domain/hook/predicate.ts`) is a separate, deliberately narrower type — `(fromPhaseId, visitCounts) => boolean`, synchronous, no I/O, called inline inside the pure `engineReducer` because it decides `EngineState.currentPhaseId` itself. Zero predicates are registered anywhere (`main.ts:53`: `{ resolve: () => undefined }`).

Both registries are built once in `main.ts:onload()` as plain resolve-only objects — independent of any Bases view's lifecycle, since hooks fire from `TimerTicker`-driven dispatches (`main.ts:55-59`), not from view rendering. This is unlike `MutableTaskSourceRegistry` (`src/timer/task-source-registry.ts`), the one registry in the codebase that *is* runtime-mutable, because its contents legitimately change per Bases `onDataUpdated` — its own doc comment explicitly contrasts itself against "`HookRegistry`/`PredicateRegistry` (populated once at plugin load)."

This design was reached over several rounds of adversarial review and grounded ecosystem research (see `flow-gu1.10`'s `bd show` design field for the full provenance). Two corrections from that process are load-bearing here and are not re-litigated below: (1) the reference class for the trust/isolation model is Obsidian's own built-in **Bases** formula/function system, not community script-runner plugins (Templater/Dataview/QuickAdd) — those operate under Obsidian's all-or-nothing "Restricted Mode" boundary, a different trust model than a first-party, on-by-default feature; (2) Bases' formula grammar is confirmed (via Obsidian's own docs) to be genuinely restricted — no assignment, no user-defined functions, no I/O, statically-rejected circular references — and is *not* embeddable or extensible by third-party plugins (no such API is shipped; it's an open, unfulfilled forum request).

## Goals / Non-Goals

**Goals:**
- Let a `Phase`'s `onEnter`/`onComplete`/`onSkip`/`onExit` resolve to a vault-authored `.js` script, executed with meaningful isolation from the Obsidian/Electron host, producing `FileMutation[]` through the existing `Hook` contract unchanged.
- Let a `TransitionCondition`'s `'custom'` predicate resolve to a vault-authored formula string, evaluated synchronously in-process, with no execution isolation needed because the grammar itself has no capability to misuse.
- Give both a discovery/binding mechanism that matches how Obsidian users already expect to configure "run X when Y happens" (grounded in Templater/QuickAdd/Shell-commands convention), without reopening this project's "never eval from settings/frontmatter" boundary.
- Make `EngineStore.dispatch`'s hook loop resilient to a script that throws or hangs — necessary once hooks stop being exclusively one hand-typed, vetted implementation.

**Non-Goals:**
- Widening `Predicate`'s inputs beyond `fromPhaseId`/`visitCounts`. Vault-state-dependent predicates (e.g. an `isRestDay` example reading a daily note's frontmatter) stay out of reach until a follow-up change adds a pre-resolved snapshot input — deliberately deferred rather than pinned down speculatively here (see Open Questions).
- Any read/write bridge that lets a script query vault state *during* its own execution (an RPC-over-`postMessage` request/response protocol was designed, then dropped — see Decisions).
- Exposing interactive prompt/modal capability to vault-authored scripts. Stays exclusive to the built-in write-back hook.
- A permission system, capability tokens, or per-mutation-type ACLs layered on top of `FileMutation[]`.
- Changing `PredicateRegistry`/`HookRegistry`'s resolution semantics (`transition-predicate-resolution`'s and `hook-execution`'s existing "unresolved name → treated as absent, never throws" requirements are untouched) — only *what* gets registered under a name is new.

## Decisions

**Two separate mechanisms, not one script runner.** `Hook` is write-capable and must defend against a script trying to reach the vault/host outside the `FileMutation[]` choke point — that needs runtime isolation (a Worker). `Predicate` is read-only-by-contract and evaluated inline inside a pure reducer — a restricted expression grammar removes the *vocabulary* to do anything unsafe, which is strictly cheaper than isolating a runtime that could never do anything unsafe in the first place. Obsidian's own Bases formulas validate this split directly: the most ambient, zero-opt-in, on-by-default feature in the platform chose grammar restriction for reads and *has no write primitive at all* — evidence that restriction doesn't scale to "safely describe a mutation," and that isolation is the right tool specifically where Bases' own team declined to go further.

**Script hooks execute inside a Web Worker; no lighter isolation considered sufficient.** Electron's renderer has Node integration; Workers do not inherit it unless a plugin explicitly opts in (this plugin doesn't). A `new Function(scriptSource)` run on the main thread could `require('fs')`/`child_process` and bypass `FileMutation[]` entirely — the Worker boundary is what makes "declarative, no imperative vault access" true rather than a convention a script can ignore in one line. *Alternative rejected: no isolation at all, matching Templater/Dataview/QuickAdd.* Correct read of that precedent, but the wrong precedent — those are opt-in community plugins under Restricted Mode's all-or-nothing gate; a Hook fires ambiently as a side effect of ordinary timer use, with no equivalent single consent gate. *Alternative rejected: QuickJS-via-WASM or another embedded interpreter.* Strictly more restrictive than needed — a non-Node Worker plus the `FileMutation[]` choke point already contains the script; a WASM interpreter adds payload size and marshalling cost for no additional safety this design needs.

> **ERRATUM (2026-07-25, tasks.md task 3.0 feasibility spike): the premise above is false in practice, invalidating this Decision as written.** A throwaway e2e test (Playwright/CDP against the real dev-vault Obsidian instance, not a simulated environment) spawned a Worker via `Blob`/`URL.createObjectURL` — the exact mechanism this design assumes — and probed it from inside the Worker's own `onmessage` handler. Result: `typeof require !== 'undefined'` is `true`, `require('fs').readFileSync('/etc/hostname', 'utf8')` succeeded and returned real host data, `require('child_process').execSync` is defined, and `typeof process !== 'undefined'` is `true`. `window`/`document` are correctly absent, but that was never the property this Decision relied on. Obsidian's `BrowserWindow` evidently runs with Node integration enabled for spawned Workers too (`nodeIntegrationInWorker`-equivalent), and that is a webPreferences setting on Obsidian's own window — not something a plugin's `new Worker(...)` call site can override per-invocation. **Practical consequence: the rejected "no isolation at all" alternative above and the chosen Worker approach provide the identical (zero) protection against `require('fs')`/`child_process`.** The QuickJS-via-WASM alternative's rejection reasoning ("a non-Node Worker plus the FileMutation[] choke point already contains the script") no longer holds either, since there is no non-Node Worker available. See the revised Open Questions entry below — this needs a new decision before group 3 (tasks.md) resumes; candidates are listed there, not resolved here.

**`HookContext` gets pre-resolved, read-only frontmatter for exactly one context-implied path — the active file's note (`EngineState.activeFilePath`) — resolved synchronously on the main thread before the Worker spawns, not via a runtime read bridge.** (Corrected during final review: an earlier draft of this decision also named "the firing phase's own note" as a second enrichable path. `Phase` (`src/domain/phase/phase.ts`) has no note/file-path field — `id`, `label`, `kind`, `duration`, `taskSourceId`, `completionPolicy`, `notification`, `logTarget`, and the four hook references are its entire shape — so there is no second path to resolve. If a phase-to-note association is wanted later, it needs its own domain modeling as a separate change; it is not something this change can silently assume exists.) An async request/response RPC protocol over `postMessage` (script calls `await vault.readFrontmatter(path)`, main thread resolves and replies) was designed in full and then dropped: the read it would bridge is *already synchronous* — `ObsidianFrontmatterReader.readValue` (used by the existing write-back hook) reads Obsidian's in-memory `metadataCache`, not disk. Building bidirectional RPC (request IDs, correlation, per-request timeouts) to cross a Worker boundary for a read that was never asynchronous in the first place buys nothing and erodes the "pure function of its input snapshot" framing for free. Pre-resolving and folding the result into the same `HookContext` payload that's already being Temporal-serialized for the Worker (below) is strictly simpler and keeps the script a pure function of one snapshot. *Constrained to the one context-implied path, not arbitrary script-chosen paths:* the risk isn't disk access (a Worker can't reach disk) — it's vault-internal exfiltration, e.g. a script reading note A's frontmatter and writing it into note B via the existing `append` mutation, a capability never obviously granted by registering a hook for one specific phase.

**`HookContext` needs an explicit serialize-to-ISO-strings/rehydrate boundary before crossing `postMessage`.** `HookContext` transitively carries `Temporal.Instant`/`Duration` (via `Session`/`PhaseInstance`), which are not structured-cloneable — a naive `postMessage(context)` throws `DataCloneError`. The Worker-side shim rehydrates these back into `Temporal` objects before invoking the script, so a script author still works with real `Temporal` values, matching this project's Temporal-over-`Date` convention; only the wire format is stringly-typed.

**Execution model: one Worker per invocation, terminated after, with a timeout — no pool.** Hooks fire only on phase transitions (`deriveHookEvents`), roughly every ~25 minutes or on manual skip/done — per-invocation spawn cost is trivial at that frequency, and terminate-after gives a hang/infinite-loop kill a main-thread `Function` could never provide, plus no state leaking between invocations (keeps hooks "pure(ish)," matching the existing `Hook` contract's spirit).

**`EngineStore.dispatch`'s hook-invocation loop (`src/timer/store.ts:82-95`) gets a `try`/`catch` around each hook's invocation, not just around `applyMutations`'s result.** Today, a hook whose returned promise rejects propagates out of `dispatch` uncaught, aborting every later fired event's hook in that same dispatch — acceptable when the only hook is one vetted, hand-typed implementation, not acceptable once user-authored scripts (which will throw and hang far more often) are in the mix. This is a genuine behavior gap in the existing `hook-execution` capability, not new-feature scope creep — see the delta spec.

**`'custom'` predicates are authored as a small formula string (comparisons, `if(cond, then, else)`, boolean operators) modeled on — but not calling into — Bases' own formula vocabulary, interpreted by a small in-repo parser/evaluator.** Bases' evaluator isn't embeddable (confirmed: no plugin extension API ships for it), so "reuse Bases" honestly means "adopt its grammar as prior art, own a small interpreter." The grammar is intentionally *not* Turing-complete: no variable assignment, no user-defined functions, no loops/recursion, no I/O — the same properties that make Bases' own formulas safe to run ambiently for every user apply here without needing a Worker, a timeout, or any serialization boundary at all. Identifier/member-access resolution in the grammar is restricted to a fixed whitelist of own `visitCounts` keys and `fromPhaseId` — not general property access — specifically to close off prototype-chain traversal (`visitCounts.constructor`, `.__proto__`) as an injection vector in a hand-rolled evaluator over user-authored strings.
**Confirmed by the user over a structured (dropdown-built) config alternative.** This track (the formula grammar and its interpreter) went through no adversarial review round — both rounds reviewed the Worker/Hook track specifically — so a structured, non-string alternative (e.g. `{ field: 'visitCounts.focus', op: '>=', value: 4 }` built from settings-tab dropdowns, no parser/tokenizer/AST, no injection surface to fence off) was raised explicitly as a simpler/safer option before committing. The user chose the formula-string approach deliberately: it's the direct analog of Bases' own formula-authoring UX (a short expression, spreadsheet-style), which is this design's explicit reference model throughout (see Context), and leaves room for more expressive/reusable authoring later if wanted, which a fixed dropdown shape would foreclose. The prototype-chain-traversal guard (below) is the concrete mitigation for the injection-surface cost of that choice.

**Predicates are configured as a name + inline formula-string pair directly in the settings tab — no scripts-folder file needed.** Unlike a Hook script (a real program, naturally a file), a predicate is a short expression; forcing it into its own vault file would be needless ceremony the grammar's restriction doesn't require.

**Discovery/binding is explicit settings-tab registration (`addSettingTab`, already wired in `main.ts:93`) for both tracks — not a vault-wide frontmatter scan, and not piggybacking on `registerBasesView`/`getViewOptions()`.** *Alternative rejected: ambient vault-wide scan for a frontmatter marker naming a script.* `HookRegistry`/`PredicateRegistry` must resolve correctly independent of whether any Bases view is open — a scan adds real costs (perf on large vaults, `metadataCache` event fan-out, last-writer-wins name collisions between two files claiming the same hook name, a startup-ordering race against `workspace.onLayoutReady`) and, more importantly, quietly relocates the trust decision into vault data one layer down: a low-friction frontmatter edit binding a name to an executable body is exactly the friction this project's "never eval from settings/frontmatter" rule (`HookRegistry`/`PredicateRegistry` doc comments) exists to preserve. *Alternative rejected: `RoutineTimerView.getViewOptions()`.* Inherently scoped to one open Bases view instance's own config — this file already has to solve "only the currently active view may safely mutate a shared plugin-level registry" once, for `MutableTaskSourceRegistry` (`registerTaskSources`/`isViewRoutineActive`); repeating that problem for hooks that must resolve whether or not any view is open at all would be solving the same architecture mismatch twice. *Chosen shape informed by ecosystem convention* (not community-plugin trust posture, just UI shape): a settings field pointing at one designated vault folder (files inside selectable by name, mirroring Templater's "user scripts folder" / QuickAdd's script picker) plus a list of named bindings pairing a script to one or more lifecycle events, each added/edited via the settings tab — structurally the closest match is Taitava/obsidian-shellcommands' per-command "Events" tab (a list of trigger checkboxes attached to one command entry, configured once, no per-firing UI), the tightest available analog to `onEnter`/`onComplete`/`onSkip`/`onExit`.

**Script source: plain `.js` files in the designated folder, not markdown+frontmatter or a fenced code block.** The earlier case for markdown was built entirely on "discovery via frontmatter scan" — since discovery is explicit settings-tab registration instead, that constraint no longer applies. Plain `.js` avoids YAML-escaping a script body and gets real syntax highlighting/editing, matching Templater/QuickAdd's own convention.

**Trust gate is at bind time, not per-firing.** Every ambient/automatic trigger mechanism found in the Obsidian ecosystem (Templater folder-templates, QuickAdd's "Run on startup" macro, Shell-commands' Events) treats registration/binding itself as the consent event — none re-confirms on every firing, and a per-run "this script wants to write X — allow?" modal on a hook that could fire dozens of times a day would be alert fatigue, not a recognized safety pattern (nothing comparable exists even for Dataview post-CVE-2021-42057). But a script-authored hook is less vetted than the one hand-typed hook this plugin ships, which *does* prompt interactively every run — so it shouldn't get *less* scrutiny than that hook got. Resolution: a one-time preview/confirmation shown when a binding is first created (review the script source, confirm trust for this binding), mirroring Dataview's off-by-default `enableDataviewJs` toggle-once-then-trust-forever model. No further confirmation on subsequent firings of an already-confirmed binding.

## Risks / Trade-offs

- [A Worker per hook invocation adds real implementation surface: a second esbuild entry point stringified/blobbed into the main bundle (Obsidian ships a single `main.js`; a naive `new Worker('./file.js')` doesn't work), a message-passing protocol, and the Temporal serialize/rehydrate boundary] → Accepted: this is the cost of the isolation the Hook side genuinely needs (see Decisions); no cheaper mechanism reviewed provides the same "can't bypass `FileMutation[]`" guarantee.
- [Constraining Hook script reads to context-implied paths only means a script can't read arbitrary vault state, even read-only, for a plausible future use case] → Accepted for this change; widening is cheap and reversible later (add another pre-resolved field to `HookContext`), narrowing after shipping a wider surface is not — matches this project's general preference for the smaller, reversible cut.
- [Predicate's restricted grammar can't express anything needing vault I/O or wall-clock/date-relative logic beyond what `visitCounts`/`fromPhaseId` already carry] → Accepted and explicit: this is why `isRestDay`-style examples remain out of scope (see Open Questions), not a gap this change tries to paper over.
- [Bind-time-only confirmation means a binding, once trusted, could later be repointed at a different script file without re-confirmation if the settings UI doesn't re-hash/re-check the bound file's identity] → Needs a concrete answer in tasks/implementation (e.g. hash the script content at bind time, re-prompt if it changes) — flagged as an Open Question below rather than decided here, since it wasn't reached in the design-review rounds this document is based on.
- [Two new mutable, settings-backed registries (script-hook bindings, predicate bindings) diverge from `HookRegistry`/`PredicateRegistry`'s existing "populated once at plugin load" shape] → Accepted as a necessary, not incidental, divergence: unlike `MutableTaskSourceRegistry` (view-owned, invalidated by Bases query changes), these are plugin-owned and rebuild from the settings list on settings change — a simpler, more testable lifecycle than event-driven cache invalidation, not a reuse of the task-source pattern.

## Migration Plan

No persisted user data exists yet for either registry (`hookRegistry`/`predicateRegistry` are both empty/static today), so there's no migration of existing bindings — only additive settings schema. Rollout is naturally incremental per tasks.md: the `hook-execution` per-invocation `try`/`catch` fix lands first (independently valuable, de-risks everything after it), then the predicate-expression-grammar track (fully self-contained, no Worker/build-pipeline dependency), then the script-hook-worker-execution track (the largest surface: Worker bundling, Temporal boundary, context enrichment), then the settings-tab UI wiring both together.

## Open Questions

- Should a bound script's identity (content hash) be checked on each load, re-prompting for confirmation if the file changed since binding? Not resolved in the design-review rounds this document is based on; needs a decision before `script-hook-source`'s tasks are finalized.
- What's the concrete shape of a pre-resolved snapshot input for vault-state-dependent predicates (deferred out of this change, per Non-Goals) — a follow-up change, not blocking this one.
- ~~Exact Worker-spawn mechanism...~~ — resolved by tasks.md's group 3 feasibility spike (task 3.0), but negatively: `Blob`/`URL.createObjectURL` spawns successfully, but the spawned Worker has full Node integration (`require('fs')`/`child_process`/`process` all functional — see the Decisions-section erratum above). This is now the **blocking** open question for group 3, superseding the one it replaces:
  - **What mechanism, if any, actually isolates script-hook execution from Node/host access in this Obsidian build?** Not resolved here — candidates surfaced during the 2026-07-25 pause, none prototyped or adversarially reviewed yet:
    1. **Sandboxed `<iframe>`** (`sandbox` attribute, no `allow-same-origin`, script delivered via `srcdoc` + `postMessage`). Electron's documented behavior is that a sandboxed iframe doesn't inherit the host window's Node integration regardless of the parent's `nodeIntegration`/`nodeIntegrationInWorker` settings — a different isolation primitive than the Worker's, worth its own feasibility spike before trusting it.
    2. **QuickJS-via-WASM or another embedded interpreter**, revisited: the original rejection ("a non-Node Worker plus `FileMutation[]` already contains the script") is exactly the premise the spike disproved. A WASM-sandboxed interpreter has no ambient host bindings to inherit by construction, at the cost of the payload/marshalling overhead the original design traded away.
    3. **Drop runtime isolation entirely; rely solely on the bind-time confirmation gate**, matching Templater/Dataview/QuickAdd's actual trust model rather than the "ambient trigger needs more than that" argument used to reject it. This design already built a one-time preview/confirm-before-trust gate for the "trust gate is at bind time, not per-firing" Decision above, independent of the Worker choice — if no cheap runtime isolation exists, that gate may already be this project's realistic ceiling, same as its ecosystem precedents.
    4. **A hidden `BrowserWindow`/separate renderer with `nodeIntegration: false`**, if reachable at all from a sandboxed Obsidian plugin (likely not, without deprecated Electron `remote` access) — included for completeness, probably not viable.
  - None of these should be assumed correct without their own spike, given how confidently the original Worker assumption was held (two adversarial review rounds) and how cleanly it was disproved.
