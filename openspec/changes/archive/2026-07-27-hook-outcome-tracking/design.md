## Context

flow-c08 (`openspec/changes/archive/2026-07-26-session-phase-instance-history`) gave `EngineState` real `Session`/`PhaseInstance` history but explicitly cut `PhaseInstance.mutationsApplied` from scope (its design.md Decision 7), flagging four open questions instead of guessing at a shape:

- **Reentrancy**: by the time a hook settles, its target instance may already be several instances back in `history`, or `session` may have gone `null` via an intervening `stop`.
- **Append-not-replace**: `onComplete` and `onExit` both fire for the same closing instance and settle independently — a second write must accumulate, not overwrite.
- **Sealing**: does a closed `history` entry keep mutating after close, visibly to subscribers (side-panel/timer views)?
- **Failure modeling**: `PhaseInstance` has no field for a failed/`invocationFailed` hook outcome — history has nowhere to record a hook that threw or whose mutations failed to apply.

Two things have changed since that design.md was written, both narrowing the actual problem:

- **flow-dez landed `EngineStore.dispatch` serialization** (`src/timer/store.ts`'s `pendingDispatch` chain). Every call to `dispatch()` now chains onto a private pending promise, so one call's full `runDispatch` — including every `await invokeHook(...)` inside its hook-firing loop — resolves before the next queued call's `runDispatch` starts. The *cross-dispatch* race that made "reentrancy" look open-ended (a second `tick`/`stop` interleaving with an in-flight hook from a different dispatch) is gone. What remains is *within one dispatch*: a single `advance-phase`/`tick`/`finish-phase` call can fire up to three events (`onComplete`/`onSkip`, `onExit`, `onEnter`) in the same `runDispatch`, awaited sequentially in `deriveHookEvents`' order. `onComplete`/`onSkip` and `onExit` target the *same* just-closed instance; `onEnter` targets the newly-opened one. A `stop` mid-phase is the one case where the target instance's `session` is `null` by the time its lone `onExit` hook settles (the same transition that abandons it also resets `EngineState` — see flow-c08 design.md Decision 9) — that's a legitimate "nowhere to write it" case, not a bug to work around.
- **`HookInvocationOutcome`'s `'applied'` stage carries no mutations of its own** (`src/timer/store.ts`): `{ stage: 'applied', result: ApplyMutationsResult }`, and `ApplyMutationsResult`'s success case is bare `{ success: true }` (`src/domain/mutation/apply-mutations.ts`). There is currently no way to know *which* `FileMutation`s a successful hook actually wrote — only that all of them, or none past the first failure, did. This has to be fixed regardless of where the fold logic lives, since "what mutations got applied" is exactly what `PhaseInstance.mutationsApplied` is meant to answer.

`applyMutations` (`src/domain/mutation/apply-mutations.ts`) already fails fast, sequentially, and its `ApplyMutationsResult`'s failure case names the one mutation (`result.mutation`) that failed.

This design went through one round of independent adversarial review before implementation (a Software Architect agent, verifying claims against the real code rather than the narrative). It surfaced three real issues, all addressed in the Decisions below rather than left as caveats: `onComplete` does not *always* target a just-closed history entry (a `manualClear`-policy phase's `onComplete` fires while the instance is still open — see Decision 3); relocating `HookInvocationOutcome`/adding `PhaseInstanceHookFailure` as first drafted would have introduced an unacknowledged `session.ts` ↔ `hook.ts` type-only import cycle (see Decision 1); and identifying "which mutations applied" by searching for the failing mutation's object reference (`indexOf`) silently mis-attributes results if a hook's returned array ever contains the same `FileMutation` object twice (see Decision 6).

## Goals / Non-Goals

**Goals:**
- Fold each fired hook event's real outcome onto the `PhaseInstance` it fired for: successfully-applied mutations into `mutationsApplied`, invocation/mutation failures into a new `hookFailures` field.
- Accumulate across multiple hook events per instance (`onComplete` + `onExit` on the same closing instance) rather than overwrite.
- No-op cleanly when the target instance is no longer resolvable in `EngineState` (the `stop`-mid-phase case), matching the existing `syncQueueExhausted`/`syncItemTouch` "unresolved external state ⇒ no-op" precedent.
- Answer the "sealing" question explicitly (see Decision 4) so the behavior is documented, not incidental.

**Non-Goals:**
- Recording a `FileMutation`'s prior value (already out of scope per flow-c08 design.md Decision 11 — unchanged here).
- Persisting `Session`/`PhaseInstance` history to disk (still in-memory-only, per flow-c08 design.md Decision 8 — unchanged here).
- Changing `applyMutations`'s fail-fast, sequential-dispatch semantics — this change only reads its existing result shape more completely, it doesn't alter how mutations are applied.

## Decisions

**1. `HookInvocationOutcome` moves from `src/timer/store.ts` to `src/domain/hook/hook.ts`, and its `'applied'` stage gains `mutations: readonly FileMutation[]`. `HookEvent` moves from `hook.ts` to `hook-reference.ts`, re-exported from `hook.ts` for existing importers.** `engineReducer`'s new `record-hook-outcome` action (Decision 2) needs `HookInvocationOutcome` to fold an outcome onto `PhaseInstance`, and `reducer.ts` importing a type from `store.ts` would invert this codebase's existing dependency direction (store depends on reducer, not the reverse — AGENTS.md's "state reducer, state store, and execution tickers live in isolated modules"). `hook.ts` already defines `Hook`/`HookContext`/`HookRegistry` and already imports `FileMutation`; it's the natural home for "the outcome of invoking one," and both `reducer.ts` and `store.ts` can import it from there without a new cycle. Widening `'applied'` with `mutations` is required regardless of where the type lives: `invokeHook` (`store.ts`) already has the hook's returned `mutations` in scope when it builds the outcome — capturing it costs one field, and without it there is no way to compute "which mutations were actually written" from `ApplyMutationsResult` alone (its success case is bare `{ success: true }`). *Alternative rejected: keep `HookInvocationOutcome` in `store.ts` and pass the raw outcome across a callback/event into the reducer.* Same information, but forces `reducer.ts` to import a store-defined type anyway, or duplicates the type — moving it once is simpler than either.
Separately, `PhaseInstanceHookFailure` (Decision 5) lives on `PhaseInstance` in `session.ts` and needs to name which `HookEvent` produced it — but `hook.ts` already imports `PhaseInstance`/`Session` *from* `session.ts` (for `HookContext`), so `session.ts` importing `HookEvent` back from `hook.ts` would be a real, if type-only (erased under this repo's `isolatedModules`/ESLint `consistent-type-imports`), `session.ts` ↔ `hook.ts` cycle — an architectural inversion worth avoiding rather than silently accepting. `hook-reference.ts` already exists for exactly this shape of problem (its own doc comment: "keeps Phase from cyclically depending on the hook execution model") and has zero imports of its own. Moving the `HookEvent` string-union there (`hook.ts` re-exports it, so no existing importer of `HookEvent` from `hook.ts` breaks) gives `session.ts` a cycle-free import path, and `hook.ts` picks it up the same way it already does `HookName`.

**2. A new store-internal-only `record-hook-outcome` `EngineAction`, folded by a pure `recordHookOutcome` function in `engineReducer`'s switch — mirroring `record-item-touch` exactly.** `EngineStore.dispatch`'s hook loop already knows, per fired event, the `phaseInstanceId` it targeted (carried on `HookEventOccurrence` since flow-c08) and the `HookInvocationOutcome` `invokeHook` just produced. After each `invokeHook` call settles, `runDispatch` dispatches `{ type: 'record-hook-outcome', phaseInstanceId, event, outcome }` through `engineReducer` and applies the result, the same "store resolves/awaits external state, then feeds it back through a dedicated action so the reducer stays pure" pattern already used by `set-queue-exhausted` (queue state) and `record-item-touch` (active-item snapshots). *Alternative rejected: mutate `PhaseInstance` inline in `store.ts` without a reducer action.* Every other piece of `EngineState` that changes after a dispatch's initial `engineReducer` call goes through this same pattern (`syncQueueExhausted`, `syncItemTouch`) specifically so `engineReducer` stays the single place that knows how to transform `EngineState` — an inline mutation here would be the one exception.

**3. `recordHookOutcome` looks up the target instance by id — `session.currentInstance` first, then `session.history` — and no-ops (returns `state` unchanged) if neither matches.** This directly answers the reentrancy question, and is now safe *because* of flow-dez's serialization (Context). The lookup is deliberately dynamic (checks both locations every time) rather than branching on event type, because event type alone doesn't determine the target: `onEnter`'s outcome always targets `currentInstance` (the instance it just opened); `onSkip`/`onExit`'s outcome and a `null`/`noOp`-policy phase's `onComplete` always target the instance that same dispatch just closed (by then the *last* entry in `history` — nothing else can have appended to `history` mid-dispatch, since no other dispatch can run concurrently) — **but a `manualClear`-policy phase's `onComplete` targets `currentInstance`, not `history`**: `completePhase` (`reducer.ts`) leaves a `manualClear` phase's instance open (`{ ...state, status: 'completed' }`, `session` untouched) until a later, separate `advance-phase` dispatch eventually closes it, and `deriveHookEvents` reads that instance's id via `requireCurrentInstanceId`, not off `history`. An implementation that "optimized" the lookup into an event-type branch (history for `onComplete`/`onSkip`/`onExit`, current for `onEnter`) would silently break every `manualClear` phase's `onComplete` outcome — the check-both-locations algorithm as specified handles this correctly without needing to special-case it. The only case where lookup fails is `stop` mid-phase: `deriveHookEvents` already documents that `nextState.session` is `null` there (flow-c08 design.md Decision 9), so there is no `Session` left to fold anything onto by the time that dispatch's one `onExit` hook settles — a real "nowhere to put it" case, not a bug. The existing `HookEventApplication` returned from `dispatch()` still carries that hook's outcome either way (`main.ts`'s `reportFailedHookApplications` already surfaces invocation/mutation failures from there) — only the `PhaseInstance`-level record is skipped, and only for a session that's already been fully discarded.

**4. Sealing: an instance keeps accepting `record-hook-outcome` folds for as long as it's targetable (`currentInstance` or the tail of `history`), and stops the moment neither is true anymore.** For most phases this window is "until the dispatch that closed it finishes its hook loop" (up to two folds: `onComplete`/`onSkip` then `onExit`, per Decision 3) — but a `manualClear` phase's instance stays targetable across dispatches, since it remains `currentInstance` (open) from its `onComplete` fold until whatever later dispatch finally clears it. Either way, sealing is structural, not enforced by a flag or a timestamp check: once `deriveHookEvents` stops referencing an instance's id at all (it's aged out of `history`'s tail into an older entry, or `stop` discarded the whole session), no future fold can target it, because nothing ever dispatches `record-hook-outcome` for an id that isn't the current fired event's `phaseInstanceId`. Subscribers (side-panel/timer views) may see a `history` entry's `mutationsApplied`/`hookFailures` grow by one or two more listener notifications in quick succession right after its close notification — all before `EngineStore.dispatch`'s returned promise resolves. This is accepted and intentional: those notifications *are* the record of the events that closed the instance, not a violation of "closed means done." *Alternative rejected: buffer all hook outcomes and apply them in one combined write after the loop.* Would hide the same information behind fewer, batched listener notifications instead of resolving the actual open question — and loses the accurate firing-order interleaving between `mutationsApplied`/`hookFailures` growing and any hook's own side effects (e.g. a write-back modal) becoming visible.

**5. Failure modeling: a new `PhaseInstanceHookFailure` discriminated union (`src/domain/session/session.ts`), not a widened `mutationsApplied` or a boolean flag.** Two distinct failure shapes exist and both need to name which event produced them: `{ event, kind: 'invocationFailed', cause }` (the hook itself threw or its promise rejected — `HookInvocationOutcome.stage === 'invocationFailed'`) and `{ event, kind: 'mutationFailed', mutation, cause }` (the hook returned mutations, but `applyMutations` stopped at one of them — `HookInvocationOutcome.stage === 'applied' && !result.success`). `PhaseInstance.hookFailures: readonly PhaseInstanceHookFailure[]` accumulates these the same way `mutationsApplied` accumulates successes — append-only, one instance-level source of truth for "did every hook that touched this instance fully succeed." *Alternative rejected: fold everything into one `hookOutcomes: readonly { event, outcome }[]` field instead of splitting `mutationsApplied`/`hookFailures`.* Would technically capture the same information (reusing `HookInvocationOutcome` as-is) with one field instead of two, but loses the "applied prefix" computation this design already needs to do to populate `mutationsApplied` in the first place (Decision 1) — a consumer wanting "just the mutations that wrote" would have to redo that computation themselves from the raw outcome trail. Two purpose-built fields, both flat arrays of small records, isn't more API surface in the sense flagged before (interfaces/registries) — it's a data shape that says exactly what happened, once.

**6. `ApplyMutationsResult`'s failure case gains `appliedCount: number`, so the "applied prefix" is computed positionally (`outcome.mutations.slice(0, appliedCount)`), not by searching for the failing mutation's object reference.** First drafted as `outcome.mutations.indexOf(outcome.result.mutation)` — reference-based lookup of the failing mutation within the original array. `applyMutations` does preserve element references through its recursion (`const [mutation, ...rest] = mutations`), so this isn't wrong for the common case, but `indexOf` returns the *first* matching index for a given reference: if a hook's returned `FileMutation[]` ever contains the same mutation object twice (nothing in `Hook`'s type or `applyMutations` rules this out) and the failure lands on the second occurrence, `indexOf` would find the first one instead and silently truncate real, successfully-applied mutations out of `mutationsApplied`. `applyMutations`'s internal recursion already knows exactly how many mutations it consumed before the one that failed — surfacing that as `appliedCount` on the failure result is a small, purely-additive widening of `ApplyMutationsResult` (its existing success case, `{ success: true }`, and existing property-level test assertions in `tests/apply-mutations.test.ts` — `result.mutation`/`result.cause`, not a full-object `toEqual` — are both unaffected) that makes the prefix computation correct regardless of duplicate references. *Alternative rejected: document/enforce that hooks must not return the same mutation object twice.* Adds a constraint `Hook`'s type can't express and a future script-backed hook has no way to know about; fixing the computation itself is strictly better than relying on every hook author to avoid a footgun they'd never suspect exists.

## Risks / Trade-offs

- [`stop` mid-phase silently drops that instance's final `onExit` hook's outcome from `PhaseInstance.hookFailures`/`mutationsApplied`, even though `HookEventApplication` still reports it via `dispatch()`'s return value] → Accepted (Decision 3): the whole `Session` containing that instance is discarded by the same `stop` transition, so there is no persisted record to fold onto regardless of this change — consistent with flow-c08 design.md Decision 8 (no persistence exists yet to lose).
- [Widening `HookInvocationOutcome`'s `'applied'` stage breaks the two existing exact-equality assertions in `tests/store.test.ts` that check `{ stage: 'applied', result: {...} }`] → Accepted; mechanical test updates (add `mutations: [...]`), not a design concern — same category flow-c08's own migration plan called out for its shape changes.
- [Multiple `applyState` calls per dispatch (one per fired hook event, on top of the existing pre-loop one) means more listener notifications per dispatch than before] → Accepted (Decision 4); each notification reflects real, distinct state (an instance's outcome trail growing), not a batching artifact to be optimized away.
- [A `session.ts` ↔ `hook.ts` type-only import cycle was a real risk of the first draft (Decision 1) — not caught by `bun run typecheck`/`bun run lint` since both edges would have been `import type`-only and this repo has no `import/no-cycle` rule, but a genuine, unacknowledged architectural inversion] → Resolved, not just accepted: `HookEvent` relocates to the already-existing, zero-import `hook-reference.ts` (Decision 1), so no cycle exists to accept.

## Migration Plan

No persisted user data exists for `EngineState`/`Session`/`PhaseInstance` (unchanged from flow-c08 design.md's own migration plan) — this is a pure code migration. The one existing `PhaseInstance` literal in `tests/write-back.test.ts` needs a `hookFailures: []` field added; the two `HookInvocationOutcome`-shaped assertions in `tests/store.test.ts` need a `mutations: [...]` field added to their expected `'applied'`-stage objects; any code importing `HookEvent` from `hook.ts` keeps working unchanged via its re-export from `hook-reference.ts`. All mechanical.
